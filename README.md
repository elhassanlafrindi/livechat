# LiveChat SaaS

A simple multi-tenant live chat service (similar to Tawk.to / Crisp).
Shop owners paste one `<script>` tag into their website. A chat bubble appears, and their visitors can talk to them in real time. The owner answers from a dashboard.

This project is also a **learning project** for: WebSocket, STOMP, Spring `@MessageMapping` / `@SendTo`, real-time notifications, JWT authentication, and multi-tenancy.

> **Guiding rule for contributors and AI agents: keep it simple.** Build the smallest thing that works, then add layers. Do not add features, libraries or abstractions that are not listed in this file without asking.

---

## 1. Business context

There are only two kinds of people. **There is no agent and no role system**: the shop owner is the only person who answers visitors.

| Who | Description | Has account? |
|---|---|---|
| **Owner** | Owns a shop website and pays for the service. Registers, creates sites, gets a `siteKey`, and answers visitors from the dashboard. | Yes (email + password) |
| **Visitor** | Person browsing the shop website who opens the chat. | No (anonymous) |

### Business flow
1. The owner registers and creates a **Site** -> receives a unique `siteKey`.
2. The owner pastes this into their website:
   ```html
   <script src="https://yourapp.com/widget.js" data-site-key="abc123"></script>
   ```
3. The **widget** (our JS, running inside the shop's page) shows a chat bubble.
4. A visitor opens the chat -> `POST /api/widget/conversations` creates a **Conversation** before the first message -> the owner gets a live notification in the dashboard at that moment.
5. The owner replies in real time. All messages are saved in the database.
6. The owner can read the history later.

### Plans (future, not in MVP)
- Free: 100 conversations per month.
- Paid: unlimited conversations and history.

## 2. Glossary

- **Widget**: a small piece of UI embedded inside someone else's website. Here: the chat bubble + chat window, delivered as a single `widget.js`.
- **Chat bubble**: the round button at the bottom-right corner that opens the chat window.
- **Site**: one customer website registered in our system. Identified by `siteKey`. This is the **tenant**.
- **siteKey**: public random string identifying a Site. Sent by the widget when connecting.
- **visitorId**: random ID generated by the widget and stored in the visitor's `localStorage`, so the same visitor returns to the same conversation.
- **Conversation**: one chat thread between one visitor and the owner of a Site.
- **STOMP**: a simple text messaging protocol that runs on top of WebSocket (adds *subscribe* and *send to destination*). Spring uses it so `@MessageMapping` and `@SendTo` work.
- **Destination**: a STOMP address, e.g. `/topic/chat/42`.

## 3. Architecture

```
livechat-saas/
├── backEnd/        Spring Boot (REST API + WebSocket/STOMP)
├── dashboard/      React + Vite + TypeScript, strict (owner interface)
├── widget/         Plain JavaScript (embeddable chat, NO framework)
├── demo-shop/      Fake shop website to test the widget
└── docker-compose.yml   PostgreSQL
```

```
Visitor (widget.js) ──WebSocket/STOMP──┐
                                       ├──> Spring Boot ──> PostgreSQL
Owner (React dashboard) ──WS + REST────┘
```

- One Spring Boot server. Spring's **in-memory simple broker** is used (no RabbitMQ, no Kafka in the MVP).
- The widget has **no framework** on purpose: it runs inside other people's sites and must stay small and conflict-free.

### Tech stack
- **Backend:** Java 21, Spring Boot 4.1.1, Spring Web, Spring WebSocket (STOMP), Spring Security (JWT), Spring Data JPA, PostgreSQL, Lombok
- **Dashboard:** React, Vite, TypeScript (strict, never `any`)
- **Widget:** vanilla JS, `stomp.js` / SockJS
- **Infra:** Docker Compose (PostgreSQL)

### Backend package layout (by feature, not by type)
```
com.livechat
├── common/exception/ ResourceNotFoundException, BadRequestException
├── config/          WebSocketConfig, SecurityConfig, CorsConfig
```

## 4. Domain model

```
User 1 ──── * Site 1 ──── * Conversation 1 ──── * Message
```

| Entity | Fields |
|---|---|
| **User** (the owner) | id, email (unique, not null), passwordHash (not null), createdAt |
| **Site** | id, name (not null), siteKey (unique, not null, indexed), allowedDomain (nullable), owner (`@ManyToOne` LAZY -> User, not null), createdAt |
| **Conversation** | id, site (`@ManyToOne` LAZY, not null), visitorId (not null, indexed), status (`ConversationStatus`, default `OPEN`), createdAt, lastMessageAt |
| **Message** | id, conversation (`@ManyToOne` LAZY, not null, indexed), senderType (`SenderType`, not null), content (TEXT, not null), createdAt |

Enums (stored with `@Enumerated(EnumType.STRING)`):
- `ConversationStatus`: `OPEN`, `CLOSED`
- `SenderType`: `VISITOR`, `OWNER`

Notes:
- `Site.siteKey` is a public random string. `Site.allowedDomain` is stored and validated as a bare hostname; enforcement comes in Step 7.
- `Conversation.visitorId` is the ID stored in the visitor's `localStorage`.
- `Conversation.lastMessageAt` is used to sort the owner's inbox.
- `Message.senderType = OWNER` always means the owner of the conversation's Site.

Multi-tenancy rule: **every query on conversations and messages must be scoped by Site**, and a User can only access Sites they own.

## 5. Authentication and security

Two kinds of people, two mechanisms:

| Who | Mechanism |
|---|---|
| **Owner** | `POST /auth/register`, `POST /auth/login` -> JWT. Passwords hashed with BCrypt. JWT sent as `Authorization: Bearer <token>` on REST, and in the STOMP `CONNECT` headers for WebSocket. |
| **Visitor** | No login. The widget sends `siteKey` + `visitorId` on STOMP `CONNECT`. The server checks the `siteKey` exists, otherwise rejects. |

Rules:
- There are no roles. Every registered User is an owner.
- A `ChannelInterceptor` (`WebSocketAuthInterceptor`) validates credentials on `CONNECT` and authorizes `SUBSCRIBE`.
- A visitor can subscribe **only to their own conversation topic**, never to others.
- An owner can subscribe only to conversations of **their own Sites**.
- The JWT is checked on CONNECT only (an expired token on an already open connection is not re-checked yet).
- CORS / allowed origins must allow the shop websites to load the widget and connect to `/ws`.

## 6. WebSocket (STOMP) contract

- **Endpoint:** `/ws` (SockJS enabled)
- **Application prefix (client -> server):** `/app`
- **Broker prefix (server -> client):** `/topic`

### Authentication (CONNECT headers)
- **Owner:** `Authorization: Bearer <jwt>`
- **Visitor:** `siteKey` and `visitorId` native headers

### Subscriptions & Permissions
- `/topic/chat/{conversationId}`:
  - **Owner:** Allowed only if the conversation belongs to a site owned by the authenticated owner.
  - **Visitor:** Allowed only if the conversation belongs to the visitor's `visitorId` and `siteId`.
- `/topic/site/{siteId}/notifications`:
  - **Owner:** Allowed only if the site belongs to the authenticated owner.
  - **Visitor:** Always rejected.
- Any other destination is rejected.

### Sending Messages
- Clients may SEND only to `/app/chat/{conversationId}` (sending directly to `/topic/**` is strictly rejected).
- The SEND payload is `{ "content": "..." }` (`senderType` is derived by the server from the STOMP session).

| Direction | Destination | Purpose |
|---|---|---|
| Client sends | `/app/chat/{conversationId}` | Send a message (`@MessageMapping("/chat/{conversationId}")`) |
| Client subscribes | `/topic/chat/{conversationId}` | Receive messages of one conversation (`@SendTo`) |
| Owner subscribes | `/topic/site/{siteId}/notifications` | Receive "new conversation" / "new message" alerts |

Message payload (`ChatMessage` broadcast and history): `{ conversationId, senderType, content, createdAt }`

## 7. REST API (MVP)

| Method | Path | Auth | Purpose |
|---|---|---|---|
| POST | `/auth/register` | public | Create owner account |
| POST | `/auth/login` | public | Returns JWT |
| POST | `/api/sites` | JWT | Create a site, generates `siteKey` |
| GET | `/api/sites` | JWT | List my sites |
| GET | `/api/conversations?siteId=` | JWT | List conversations of one of my sites |
| GET | `/api/conversations/{id}/messages` | JWT | Message history |
| POST | `/api/widget/conversations` | siteKey | Visitor starts or resumes a conversation (by `visitorId`) |
| GET | `/api/widget/conversations/{id}/messages?visitorId=...&siteKey=...` | public (visitorId + siteKey, both required) | Visitor message history scoped by Site |

## 8. MVP scope

**In scope**
1. Basic real-time chat between two browser tabs (in-memory broker)
2. Save messages in PostgreSQL
3. Sites and conversations (multi-tenancy with `siteKey`)
4. JWT authentication for owners, anonymous visitors
5. Owner dashboard: login, conversation list, chat window, live notifications
6. Embeddable widget (`widget.js`)

**Out of scope for now** (do not implement unless asked)
- Agents, team members, roles, invitations
- RabbitMQ / external broker, Kafka, Apache Camel
- Multiple backend instances / horizontal scaling
- Payments and plans enforcement
- File uploads, emojis, chatbots, analytics
- Email notifications, "typing..." indicator

**Possible later steps:** agents/team members, RabbitMQ as STOMP broker relay (to run several instances), Camel route to push chats to Kafka/Slack, typing indicator, email transcript, plans and billing.

## 10. Local development

| Part | Port |
|---|---|
| Backend | 8080 |
| Dashboard (Vite) | 5173 |
| Demo shop | 5500 |
| PostgreSQL | 5432 |

```yaml
# docker-compose.yml
services:
  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: livechat
      POSTGRES_USER: livechat
      POSTGRES_PASSWORD: livechat
    ports:
      - "5432:5432"
```

Run:
```powershell
docker compose up -d          # start PostgreSQL
cd .\backEnd
.\mvnw.cmd spring-boot:run

# In another terminal, from the project root:
cd .\dashboard
npm install
if (-not (Test-Path .env.local)) { Copy-Item .env.example .env.local }
npm run dev
```

The dashboard uses React + Vite + TypeScript in strict mode, runs at `http://localhost:5173`, and reads `VITE_API_URL=http://localhost:8080` from `dashboard/.env.local` (ignored by Git).
